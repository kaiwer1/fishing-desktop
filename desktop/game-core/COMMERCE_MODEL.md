# Schema 2：拥有的抄网与菜单补给内核

这是原有浮钓日志内核的增量格式。它提供购买、装备和食用的事务基础；菜单、报价编号、GameOwner 授权及迁移文件流程由宿主接入。测试只使用新建私有夹具，不读取、替换或启用个人存档。

## 不变的历史

- 外层文件头仍为 `FDGJ0001`，哈希链和帧结构不变。
- `FLTJ` 载荷 schema 1 的初始记录、原有六类命令及其指纹编码保持原字节。测试用发布提交 `3b78190` 的旧内核独立生成了固定样本 SHA256，再与新内核逐字节编码结果的摘要比较。
- `FloatGameRules.Version`、规则签名和已捕获鱼的固定卖价不变。补给使用独立的不可变 `FloatCommerceCatalog`，不能借新商品价格重算旧鱼价值。
- 旧记录不重发、不压缩、不重编号。`Sequence == Receipts.Count` 继续成立，升级本身新增一个有请求与事件身份的收据。

## 单向升级

日志允许两种起点：原有 schema 1 genesis，或调用方明确创建的 schema 2 genesis。schema 1 只有追加一次 schema 2 `UpgradeFloatProfile` 才能转入 schema 2；其后的六类旧命令也使用 schema 2 载荷。提前出现的 schema 2 普通命令、升级后的 schema 1 命令、第二次升级均拒绝。

升级命令携带新的分支 ID、空食品堆叠 ID、补给目录，以及旧分支、源长度、源序号、完整源文件 SHA256 和源末帧摘要。`FloatGameStore.Execute` 与 `AppendUpgrade` 在持有文件句柄时核对实际前缀长度、完整字节摘要及末帧摘要；回放再次对升级帧之前的实际字节执行同一核对。单纯伪造命令字段或重新计算外层帧哈希不能绕过核对。纯 reducer 没有文件权限，只验证状态与命令；它的候选必须由 store 确认。

文件迁移服务应先检查关闭的源日志，备份其冻结字节，再创建新候选并复制完整旧前缀，最后调用 `AppendUpgrade`。内核不会判断路径是否为原始个人存档，因此直接对旧文件调用该方法仍有写入能力；宿主迁移服务必须强制新路径、不可覆盖和显式启用边界。内核不自动创建备份、选择文件、恢复会话或激活候选。

升级保留钱包、体力、鱼饵数、所有原资产、鱼护、收据、未结束抛投以及待放流鱼。新增抄网为空、未装备；食品数量为零。空堆叠身份只是持久化标识，不是赠送物品。旧分支命令被拒绝；换成新分支重用旧请求则发生指纹冲突，旧收据不改写。

升级载荷仅含固定有界身份、摘要和目录，不把整段历史放进单个载荷。原有单载荷 64 KiB、文件 16 MiB、10,000 笔事务限制保持不变。容量不足时拒绝升级，不清除历史腾出空间。当前容量边界测试使用反射注入私有计数器；它验证确定拒绝路径，不代表真实磁盘满测试。

## 拥有关系与操作

`FloatGameState.CreateNewWithCommerce` 的钱包、体力、鱼饵和钓组均必须由调用者明确给定。它只允许无抄网、零食品的新档。没有默认钱包、自动补给或旧档兜底赠送。

| 操作 | 变化 | 必须满足 |
| --- | --- | --- |
| `BuyFloatSupply(Net)` | 扣钱，创建一个抄网实例 | 未拥有抄网；新 ID 未被任何资产或历史鱼使用；一件上限 |
| `EquipFloatNet` | 改变装备引用 | 指向自己拥有的网；空引用表示卸下；不购买、不删除 |
| `BuyFloatSupply(Bait)` | 扣钱，向原鱼饵堆叠加整包数量 | 正整数包数，乘加不溢出，不超堆叠上限 |
| `BuyFloatSupply(Food)` | 扣钱，向固定食品堆叠加数量 | 不直接恢复体力，不自动食用 |
| `UseFloatFood` | 消耗一份食品，按目录恢复并截断至体力上限 | 有食品，堆叠归自己所有，体力未满 |

所有补给、装备和食品操作都拒绝活动抛投与待处理鱼。原来的卖鱼操作同样不能绕过会话边界。购买与装备相互独立，装备状态不能从曾经使用过开发训练网推导。

宿主使用内部 `FloatPurchaseQuote.Create(state, product, packCount)` 冻结报价。报价绑定 profile、branch、当前状态序号、目录版本及完整签名、商品、包数、实际数量与总价。reducer 再计算价格和数量，拒绝伪造值、过期报价、不同目录和数量溢出。页面后续只能引用宿主保存的报价编号；公开的报价类型没有公开构造函数。命令完整指纹还绑定新抄网 ID。任何成功事务使旧报价失效。

测试用原创试验目录：抄网 2400 最小货币单位，鱼饵每包 5 个/20 单位，食品一份 20 单位、恢复 20 体力，每次最多 100 包。若 100 单位表示一枚银币，这分别是 24、0.20、0.20 银币。目录没有硬编码进 reducer；这些数值并非 RF4 还原或平衡性结论。

## 保存与失败

所有成功操作使用原有请求/事件去重和追加后 `Flush(true)` 确认路径。相同请求完整内容重试返回已有收据，不重复扣款或消耗；同请求改内容拒绝；不同请求复用业务事件也拒绝。已知未写失败允许原命令重试。写入可能已发生时禁用该 writer，由显式重新检查决定结果，不能在仍不确定时补发购买或升级。

`test-commerce.ps1` 覆盖新档、无赠送迁移、持久化、旧分支重试、活动/待处理会话、伪造报价、数量和货币边界、资产唯一性、全体 schema 2 截断前缀、模式切换、实际前缀证明、确定/不确定写入，以及保留残缺候选。原 reducer、codec、store、owner、lifecycle、archive 套件仍独立验证原行为。

当前范围不含损坏、丢失装备、动态库存、交易税、服装、批量食用或破产救济。旧档若没有足够钱且没有可卖鱼，迁移不会自动解决其补给困难；需另行设计明确的玩法规则。
