## 页面与保存寿命

owner在创建线程上串行操作；一个只读slot、一个交互slot，view、文档及控制许可都是不可从字符串重建的对象身份。重开同角色替换旧ticket，重载文档撤销其旧许可，旧关闭/取消不会撤销新ticket/许可。关闭所有显示页也不关闭保存文件、退款或终结已出手会话。

`GrantControl`是宿主入口，不能作为任意页面消息直接暴露。`ExecuteUser`先核当前view/document/lease和宿主资格，才查询历史回执；允许原出手、收竿、放流、出售，以及已接入的购买补给、装备抄网、食用、schema3换槽/移线和装备出手命令。Host鱼事实、脱钩事实、末端损失事实、Recovery和格式升级仍被用户通道拒绝。WebView适配须另外限制来源/导航、握手及输入时序，不可把这些C#类型当成完整浏览器授权实现。

默认HostPaused=true，解除暂停不会自动恢复输入许可。宿主暂停撤控制许可并阻止页面写入；MenuOpen/满护结果仅冻结模拟资格，新Cast被拒绝，已授权菜单出售或当前鱼放流仍可走业务校验。历史回执只返回原结果和最新状态；旧授权不能利用回执查询绕过资格。

schema3 菜单换槽和整段移线仅在没有活动会话及待处理鱼时允许；菜单暂停不等于装备业务忙碌，已有控制许可的空闲玩家可以编辑。页面意图只携带已拥有的实例选择与当前状态序号，宿主冻结装备/库存版本并生成持久请求身份。已知未写入时只允许明确重试原命令或取消，不能以新操作悄悄替换；未知写入仍采用下述统一冻结规则。schema3 `CastFloatWithEquipment` 受与旧出手相同的菜单门槛，另外由准备和 reducer 检查完整装备、实际已装线量及资源。

`CanSimulate`只是此层的组合资格，不是实际时间推进、页面可见或已获得输入许可。菜单/满护不自动结束会话，动作运行时还须清除持续输入。C#内部快照含完整不可变数据状态；**页面适配通过FloatPageProjection及各功能的有界投影发送显示数据，不直接序列化State及整个Receipts历史**。后续接入的抛投、漂相和遛鱼由宿主活动时钟推进，仍需遵守这些资格边界。

保存不确定时owner撤销控制、置HostPaused，并给出Faulted且State=null的快照，不继续向页面发布旧内存为新的已确认状态。该实例不能恢复写入；关闭并重新核验原文件。回执和写入确认边界继承[文件保存候选](STORAGE.md)。

`HostFloatTerminalLoss` 与其他 host 事实一样，新提交必须有当前可模拟资格；菜单或宿主暂停时拒绝，已记录原请求的精确回执查询不重复写入。该命令仅接受当前普通会话和当前已装线/修订，不能替换满护待处理鱼；所有会话、装备、库存及目录版本仍由 reducer 核验。成功产生终结收据 `TerminalLost`，其 `EquipmentLoss` 记录线量和部件损失，`FishIds` 为空。损失 event/encounter 与请求、会话及资产身份分离，并在后续历史中双向保留，不能作为新鱼、抄网、会话、请求或事件再次使用。

当前仅实现核心提交入口，没有宿主运行时的损失票据或页面重试流程，也不把求解器故障解释成断线。写前已知失败可在原 owner 中用同一命令明确重试；若此时关闭进程，未落盘的损失事实不会保存下来，下一次 `OpenExisting` 仍会按普通已付费会话执行 Recovery，保留原装备且不退款。完整帧已写但确认未知时，重开能重放一次损失并保持缺件；部分帧则拒绝打开。没有额外 writer、隐式 Arm、跨进程未落盘结果恢复或真实断电保证。

## 启动和退出

`CreateNew`与`OpenExisting`分开，缺失/坏档不会初始化。OpenExisting先打开并重放原日志，再调用显式Startup收束：

宿主可用内部 `requiredSchemaVersion` 入口，在持有原日志写锁后、执行 Startup 前核对所需格式；当前装备宿主要求 schema3。格式不符直接拒绝，不先收束旧会话，也不自动升级或补造装备。普通旧入口仍保留原 schema1/2 打开语义。schema3 中没有会话的缺件装配重开时不写新事务、不补回缺件；普通活动会话和满护结果仍按下表处理，装备账本保持不变。

| 已确认状态 | Startup / OwnerShutdown行为 |
| --- | --- |
| 无活跃会话，含已入护/已卖鱼/已确认末端损失 | 不新增事务，保留全部现有资产/缺件/损失回执，返回no-active-session |
| 已出手但没有已确认结果的活跃会话 | host-only RecoverFloatSession一次终结，记录StartupInterrupted或OwnerShutdown原因；不退饵/体力、不补线、不发鱼/奖励 |
| 已确认满护容量拒绝，存在PendingFish | 保留同一pending结果、旧鱼护和成本，不写新事务；返回pending-result-preserved，恢复后继续结果暂停，重新授权才能明确放流 |
| 保存容量不足或无法确认收束 | 不宣称启动可玩/退出已保存；保留原因和原档，不新建或自动退款 |
| 帧内损坏或未知版本 | 按存储层拒绝打开，不自动剪尾或回退 |

2026-10-27在接线时调整此前“仅容量拒绝也在重启时收回”的设计：**已确认待选择结果继续保留**，避免关应用丢失一个已经确定的结果；普通未完成模拟仍采用恢复收竿。已同步P4/库存/玩家流程合同。此调整未迁移真实玩家数据。

Recovery原因写入命令指纹和schema1新增type6事件；无效原因、会话/版本不匹配拒绝；直接对pending调用Recover也拒绝，不能把宿主恢复当成隐式放流。已确认终结/恢复优先，重放不再结算。Lifecycle每次只尝试原命令一次，保存不确定就原样抛出，不换ID补偿。

正常退出须显式调用`Shutdown()`并确认结果；它在停止新输入后收束，独立于模拟暂停资格。`Dispose()`只释放资源，不偷偷提交事务；因此意外释放后重新打开仍须走Startup。已经确认的pending可以安全保留到下次打开。可选宿主模式已接显式退出，隐藏WebView联合验证普通活跃会话只收束一次；异常退出不补写Recovery。正式用户错误恢复/超时交互仍待完善。
