# 为当前一竿预留结算空间

存档仍保留10000笔事务和16MiB的上限。新的写入准入检查不会压缩、删除历史或增加这个上限；旧日志重放也不应用新准入规则。

唯一文件Store在每个新候选写入之前，先核对本帧容量，再根据候选会话预留后续空间：

| 候选状态 | 后续预留 |
| --- | --- |
| 没有会话 | 无 |
| 正在钓鱼 | 两笔、482字节 |
| 鱼护满，当前鱼待放流 | 一笔、188字节 |

当前编码下，最长鱼获结果帧294字节，随后明确放流188字节；收竿、恢复、脱钩和最长末端损失帧均在482字节内。新抛竿总预算因此是三笔，schema1/2为670字节，schema3为694字节。专用测试以实际编码核对这些边界；未来新增会话终结类型或修改编码时必须同步调整。

只读 `FloatSaveBudget` 供宿主检查。蓄力开始和出手确认前都会复核；真正写入仍在Store锁内重新判断，读取预算并不占位或赋予输入权限。预留不足返回 `save-settlement-reserve`，不写入、不扣饵和体力。已确认请求的查询不受门槛影响。

当前竿的最后收竿、恢复或放流不会套用新抛竿的三笔门槛。允许带活动竿的旧1→2升级同样不能消耗结算预留：新候选在创建任何输出前拒绝；旧版本已经合法生成的候选仍可只读核验。2→3升级本来只接受空闲源。

历史上已写满且仍有活动竿的档案只保持可读，不会自动修复，也不能假称这项检查解决了长期容量。后续需要明确的续档/恢复方案，保留原档与完整来源。此预留也不保证真实磁盘仍有空间，不替代写入失败处理。
