# R1：单套浮漂钓组的装配、物品归属与出手消耗

2026-10-24。状态：独立实现合同，尚未编码或通过玩法验收。本文补齐 [开发计划](DEVELOPMENT_PLAN.md) 中 P1 的钓组/库存规格前置，并衔接 P3 的[抛竿会话合同](CASTING_FLOW_SPEC.md)。P0 的宿主路线验收门槛保持不变，暂停中的界面和业务草稿不因这份规格恢复开发。

首个范围是一根带渔轮的浮漂竿、一份经典浮漂装配和一个活跃抛投会话。无轮手竿、底钓、路亚、三竿、交易、制作、维修及完整损耗物理在各自阶段接入。本文定义它们需要遵守的物品归属边界，不提前实现这些功能。

## 数据对象与守恒要求

| 对象 | 必要信息 | 不变量 |
| --- | --- | --- |
| 物品型号 `ItemDefinition` | `definitionId`、类别、适用钓法、连接类别、必要兼容参数、`rulesetVersion` | 描述型号，不代表玩家拥有一件物品；没有库存数量和装配位置 |
| 装备实例 `ItemInstance` | `instanceId`、`definitionId`、状态版本、耐久状态、当前位置 | 同型号可以有多件不同实例；每件实例同一时刻只有一个直接归属位置 |
| 鱼饵堆叠 `BaitStack` | `stackId`、`definitionId`、整数份数、状态版本 | 份数非负；选择鱼饵不复制整包，也不立即扣除一份 |
| 未绕线库存 `LineStock` | `stockId`、线型号、剩余长度、状态版本 | 长度非负；绕线分配与库存长度减少在同一次提交中完成 |
| 可用线段 `LineSegment` | `segmentId`、线型号、长度、原库存来源、状态版本、位置 | 一份线段只能在一个线杯或一个库存位置；不能同时作为两份可用长度存在 |
| 浮漂钓组 `FloatRig` | `rigId`、`rigRevision`、槽位引用、所选鱼饵堆叠、规则版本 | 引用现有实例，不把型号 ID 当作装备实例；主线从已装渔轮的线杯取得，避免另复制一份槽位库存 |
| 抛投会话 `CastSession` | `sessionId`、钓组 ID/版本、装备快照引用、规则版本、所选鱼饵、阶段、释放/提交身份 | 准备阶段不授予物品；一次会话最多提交一次出手消耗 |

长度统一用整数毫米，线径用整数微米，质量用整数毫克；界面可换算为米、毫米和克。份数和版本为整数。体力使用本项目固定整数刻度，其每次出手成本由规则版本配置。未知参数不得当作零，也不得在校验时使用随意默认值。

装备的直接位置只能是库存、钓组槽位、容器内位置或明确的不可用状态之一。渔轮拆离钓组时，线杯中的线仍随同一渔轮实例移动；它不会重新生成一卷新线。位置关系不得形成环，钓组和容器引用必须指向存在的实例。

绕线将一段长度从 `LineStock` 转成一个新的 `LineSegment`；装配已有线段则移动同一实例。拆下可用线段时保留其 ID、长度和状态，回到可用线段库存，不自动并回一卷全新的商品线。库存剩余长度、已装长度及回收线段长度的总和，只能因明确的新增、损失或移除记录变化。每次抛竿的放线和收线属于同一线段的运行状态，不重复扣整卷线，不复制线段。

鱼饵槽是选择引用，不能视作又拥有了一包鱼饵。未来多竿若共享同一堆叠，应在同一个状态持有者中校验剩余份数并结算；本阶段不启动三份并行会话。

## 可编辑装配与可抛竿就绪必须分开

`ValidateAssembly` 检查一份装配能否被保存：实例是否存在、类别是否匹配、是否有重复归属、已提供部件之间是否兼容、数量及长度是否守恒。成功后允许保存仍有缺件的装配。

`EvaluateCastReadiness` 在有效装配之上检查必需槽位、鱼饵份数、体力、当前会话、可用线长、落点和规则参数是否齐全。缺件装配可以继续编辑，但不能创建有效的出手提交。

总抛投质量等依赖整套部件的检查，只在所需部件齐全后评估；暂时缺钩不能被错误地当成“整套质量过低”而禁止保存。已存在的两件部件若有确定的类别或连接冲突，仍须立即拒绝。目录缺少必要兼容规则与玩家尚未装齐部件是两种不同原因，不能靠填零掩盖前者。

例如：取下鱼钩后，鱼钩回到库存，钓组保持可编辑并显示“缺少鱼钩”；把拟饵放入鱼钩槽、把同一个鱼钩同时交给两个归属位置，则拒绝整次修改。二者不能都笼统显示为“保存失败”。

## 第一套带轮浮漂的槽位与兼容表

| 槽位/关联 | 首套要求 | 可保存条件与就绪条件 |
| --- | --- | --- |
| 鱼竿 | 必需，一件 | 型号明确支持本项目 `float_classic` 钓法和带轮装配；连接类别匹配所选渔轮 |
| 渔轮 | 必需，一件 | 使用首套规则允许的渔轮类别；实例有唯一归属，线杯状态可读取 |
| 主线 | 必需，一个线段 | 实际装在当前渔轮；线型号及线径有对应容量规则，长度大于零且不超过该组合容量 |
| 前导线 | 首套可选，至多一件 | 省略表示主线直接接钩；若安装，连接类别和型号明确支持本钓组，长度与状态有效 |
| 鱼钩 | 必需，一件 | 类型为单钩且支持浮漂装配；通过该型号的鱼饵类别兼容表 |
| 浮漂 | 必需，一件 | 型号明确支持本套装配；有可供校验的配重范围和状态 |
| 沉子 | 必需，至少一件 | 每件沉子是不同实例；总配重落在该浮漂规则允许范围内，不因原客户端有两个引用而强制两件 |
| 鱼饵选择 | 必需，一个堆叠引用 | 型号符合鱼钩允许的饵类；真正出手前至少剩一份 |

容量、配重和钩饵适配使用本项目显式规则表：

- 线杯容量由“渔轮型号、线类别、线径”对应的允许长度给出。首套只开放已有规则的组合；未配置的线径不套用猜测的原版容量公式。
- 浮漂的允许沉子总质量范围由本项目目录规定；竿的允许抛投质量范围与各装配部件质量也来自该目录。超过明确范围的修改拒绝，缺少必要参数则标为配置缺失。这里是首套兼容检查，尚未声称模拟真实浮力或恢复 RF4 物理公式。
- 鱼钩与鱼饵按明确类别和允许关系匹配，不从显示名称或“数字越大/越小”推断钩号顺序。
- 线强度、竿承重、泄力和耐久损耗的完整关系交给 P4。本文不发明“线比竿强就一定不能装”等未经定义的硬性限制；实际出手所必需的可用状态仍必须校验。

不兼容修改返回具体槽位、原因及关联实例，整次操作不改变原装配。缺件、无饵等就绪原因可以同时返回，按槽位稳定排序；界面展示理由，不靠异常字符串猜测。

## 装配命令与会话状态限制

所有写入由唯一状态持有者处理，页面提交请求和预期版本，不能直接改库存对象。该要求承接 P0 的共享状态研究，但独立计数器日志格式不能直接称作已完成的游戏存档。

| 当前阶段 | 装配修改规则 | 资源处理 |
| --- | --- | --- |
| 无活跃会话、就绪或未就绪 | 允许替换、拆卸及选择鱼饵；重新评估就绪 | 不扣出手用饵和体力 |
| 蓄力、已松开但未出手 | 先接受取消并使旧出手身份失效，再按最新版本执行装配命令 | 取消零出手消耗；装配校验失败时原装备不变 |
| 已出手、飞行、等待、咬钩、遛鱼 | 返回 `rig-busy`，要求按收竿/失败流程结束该会话 | 不能借换件取消已提交消耗，不能自动补回线或装备 |
| 待确认结果或资源结果不确定 | 先完成结果确认或按保存恢复合同恢复 | 不允许用换装绕过待结算状态 |

取消和替换是两个有次序的结果：取消已经成功后，后续换件失败不会把旧蓄力会话恢复。每一步的请求身份和返回状态必须明确，不能向玩家展示“换装失败”同时偷偷继续原抛投。

一次替换在同一笔提交中完成“旧件回库存、新件进入槽位、引用更新、库存/钓组版本递增”。任何存在性、兼容性或版本检查失败均不改变这些对象。拆卸渔轮带走其线段关联，不把线段再列为额外新获得的物品。

示例命令（ID 仅用于说明本项目结构）：

```json
{
  "type": "ReplaceRigSlot",
  "requestId": "ce3a9944-c06c-4370-84ae-8f8bc4984a34",
  "rigId": "f14d8949-f4b6-44b1-8d9e-9720477c2ef4",
  "slot": "hook",
  "newItemInstanceId": "339ea462-97ac-49ce-b773-a609a152d742",
  "expectedRigRevision": 7,
  "expectedInventoryRevision": 31
}
```

同请求 ID、同命令内容重试返回原提交结果；同 ID 改内容返回 `request-conflict`。版本冲突返回最新可读状态，由界面明确重试，不以“最后写入覆盖”为方式丢弃其他状态变化。旧页面或已撤销授权的请求在进入业务层之前拒绝，不能通过已有请求 ID 取得新的写入权限。

## 出手消耗合同

本项目沿用已确定的原创规则：**每次成功提交出手扣一份所选鱼饵，并扣该规则版本规定的体力；出手前取消或提交校验失败都不扣这些资源。**这不是对 RF4 原版扣除时点或数值的断言。

开始蓄力时记录钓组版本、规则版本和装备引用；松开时冻结力度与落点，并进入准备出手。选择或展示鱼饵不会提前扣除，也不创建一份可再次入库的“临时鱼饵物品”。

出手事件只对当前、尚未取消且尚未提交的会话有效。提交前重新核对：

1. 会话和出手身份仍有效，当前阶段允许提交。
2. 钓组版本、引用、归属和规则版本没有变化。
3. 装配完整兼容，已有主线足以满足本次允许的放线需求，目标水面仍有效。
4. 所选鱼饵堆叠仍存在且至少一份，体力达到本次规则要求。
5. 保存层能够接受这笔原子提交；确认之前不向页面报告已成功出手。

资源份数、体力差额、会话“已提交”状态和请求回执作为同一笔事务保存。体力成本由状态持有者根据冻结的规则版本取得，不接受页面自行传入的更低成本。动画出手只提供触发信号，不拥有直接扣资源的能力。

```json
{
  "type": "CommitCastRelease",
  "requestId": "ef469b38-1ab4-49fc-bc95-01b103395208",
  "sessionId": "a451b929-d048-402b-824b-f439dbe0e2ac",
  "releaseEventId": "40533dcf-a831-4884-8ab7-3d0204ab86c8",
  "expectedRigRevision": 8
}
```

成功回执包含提交序号、原请求 ID、会话 ID、实际消耗、装配版本及提交结果；重试返回原回执并标记重复，不创建第二次飞行或再扣一次鱼饵。会话已经提交后，即使用新的请求 ID 再发送旧出手事件，也必须按会话身份拒绝重复提交。

| 结果 | 鱼饵与体力 | 装备、线和奖励 |
| --- | --- | --- |
| 按下、蓄力、松开但尚未提交 | 不扣出手消耗 | 不生成新装备、鱼或奖励 |
| 出手前取消、失焦、菜单取消、校验失败 | 零出手消耗 | 原实例与长度保留；旧回调无效 |
| 成功提交，随后正常落水 | 扣一份饵及配置的体力一次 | 沿用同一钓组和线段，进入后续会话 |
| 成功提交后轨迹受阻、落点失效或主动收竿 | 保留已提交消耗，不套用出手前退款 | 明确终止原因；不授予鱼或奖励，不自动补线、补装备 |
| 断线、脱钩或其他后续失败 | 不退这次已提交的出手消耗 | 线长/部件损失必须由后续损失规则单独且只结算一次；本规格不把尚未实现的损失公式当成已完成 |
| 保存报错且是否落盘不确定 | 不直接退款或重新扣款 | 停止后续写入，通过恢复和原请求 ID 查询确定结果，不能继续飞行后再盲目重试 |

一次出手对应一份消耗和一个会话。鱼钩、漂、沉子、渔轮与主线不会每抛生成新库存实例；动态鱼线的渲染节点不是可入库物品。鱼和经验只能在之后明确的收鱼结算中授予，不属于出手提交。

## 保存、重启与迟到事件

出手前尚未提交的会话在重启后作废，装配按已保存版本恢复为待就绪检查，不自动恢复按住状态或补发旧出手事件。已经提交但客户端未收到回执的请求，通过同一请求 ID 返回原结果，不能重新扣除。

本合同给首版的中途重启规定一个明确收束：已提交而未完成的垂钓会话在恢复时执行一次 `recovery-retrieve`，保留已经确认的鱼饵和体力消耗，结束该会话且不授予鱼或奖励。未提交的损失不得被凭空补记；已经确认的物品损失不得回填。恢复结果可向玩家查看。以后若支持中途物理状态继续运行，须另写 P3/P4 恢复规格并迁移版本，不能默认重新抛一次代替恢复。

取消、出手提交、主动收竿、恢复收竿及后续结果都用会话 ID 关联，终结事件只能结算一次。旧宿主、旧页面、旧装配版本和已结束会话的迟到动画回调均不得创建可用物品、恢复资源或再次授予奖励。

这只是待实现的业务恢复合同。P0 诊断目前没有真实断电和磁盘满验收，也不能检测所有日志截短与丢失；正式保存格式、备份和提交证明仍需 P1 单独完成，不能借本规格把它们标为通过。

## 错误与玩家可理解的原因

| 错误码 | 触发例子 | 处理与状态变化 |
| --- | --- | --- |
| `item-not-found` | 被引用实例不存在 | 拒绝修改，刷新可读库存 |
| `item-already-owned` | 同一实例已在另一槽位或容器 | 拒绝重复归属，不复制实例 |
| `slot-type-mismatch` | 把拟饵放进鱼钩槽 | 原装配不变，指出错误槽位 |
| `incompatible-components` | 竿轮连接不符、钩饵组合不支持 | 原装配不变，指出两件相关物品 |
| `missing-component` | 钓组没有鱼钩 | 可保存为未就绪；出手请求拒绝且零消耗 |
| `line-capacity-exceeded` | 安装长度超过已配置组合容量 | 拒绝绕线/装配提交，不减少线库存 |
| `insufficient-line` | 当前线段不能支持本次放线需求 | 出手前拒绝；不凭空延长主线 |
| `bait-empty` / `stamina-insufficient` | 少于一份饵或体力不足 | 出手前拒绝，鱼饵及体力均不扣 |
| `rig-busy` | 已在飞行或遛鱼时要求换件 | 要求先按当前会话的收束流程结束 |
| `stale-rig` / `stale-inventory` | 界面提交旧版本 | 不覆盖新状态，返回当前版本 |
| `session-ended` / `release-already-committed` | 取消或出手后的迟到动画事件 | 不产生新消耗、飞行或奖励 |
| `request-conflict` | 重用请求 ID 却改变内容 | 拒绝该请求，不覆盖原回执 |
| `configuration-missing` | 缺容量、配重或体力成本规则 | 禁止受影响的就绪/出手操作，不能按零成本继续 |
| `persistence-uncertain` | 保存层不能确认提交结果 | 停止业务写入并进入恢复，不自动退款或重新提交 |

保存层的已知容量不足与“结果不确定”应分开返回；如果确认没有开始写入，保留查询原回执的能力。具体生产错误码由 P1 保存接口确定，不把诊断计数器的 10000 条限制直接带入游戏设计。

## 待实现的场景验收表

| 场景 | 必须观察到的结果 |
| --- | --- |
| 拆下鱼钩并保存 | 原鱼钩回库存一次，钓组可编辑但未就绪；抛竿提示缺钩，零消耗 |
| 将同一鱼钩装到第二个位置 | 拒绝重复归属，原位置、数量和版本没有部分变化 |
| 原子替换渔轮 | 旧渔轮及其线段关系保留，新渔轮进入槽位；任何失败都不复制线段或留下半次替换 |
| 绕线超出库存或容量 | 线库存与已装长度都不改变；错误指向实际不足原因 |
| 更换不兼容钩饵或超范围配重 | 原装配保持，列出原因；不能保存成表面就绪的无效钓组 |
| 蓄力时取消再换件，随后旧出手事件到达 | 新装配不受旧事件影响，无飞行、无出手消耗 |
| 松开后、出手前装备版本或资源变化 | 再校验失败，鱼饵与体力均不扣，不发射旧装配 |
| 成功出手后同请求重复到达 | 只有一份饵和一次体力消耗，返回原回执，只存在一个逻辑会话 |
| 换一个请求 ID 重发相同会话的出手事件 | 会话级防重拒绝，不绕过请求级去重 |
| 保存成功但确认消息丢失，随后重启重试 | 原消耗保留且不重复；已提交会话只执行一次恢复收竿，无鱼或奖励 |
| 已出手后落点失效或主动收竿 | 明确失败/结束原因，已提交消耗保留；线和装备不复制、不自动补满 |
| 保存失败且结果不确定 | 不继续新业务写入；恢复确认后再决定结果，不能同时退款与重试 |
| 只剩一份饵，两个请求从同一旧状态提交 | 至多一笔提交成功，份数不为负；另一笔得到冲突或不足原因 |
| 反复装备、拆卸、抛出和收回 | 装备 ID、线段长度总量、鱼饵份数和消费记录可逐项对账 |

这些是验收要求，当前没有把任何一项列为已通过的游戏测试。真实鼠标、动画质量、浮漂物理和桌面交互还须分别按原阶段验收。

## 0.3.1 迁移边界

P1 实现前须只读确认已发布 0.3.1 的实际保存结构，列出余额、库存、鱼护、记录和装备选择的可迁移字段，并保留迁移前原始备份。本文没有读取或变更用户个人存档，也不把 RF4 类型信息作为旧原型存档格式的证据。

旧型号选择不能直接伪装成已拥有多件装备；新实例 ID 必须通过可重复识别的迁移映射产生，重复迁移不能重复发物品。旧数据没有的线长、耐久、装配细节必须逐项写明迁移政策，不能悄悄采用满线、满耐久或额外赠品。迁移失败保持原文件可用，不覆盖成空进度。

本规格只规定迁移不得丢失和复制的边界。菜单买卖、库存/鱼护原子结算及旧资产迁移回退语义见[库存与交易合同](INVENTORY_TRANSACTION_SPEC.md)；完整保存格式与实现仍属于 P1，制作合同在后续阶段补充。
