# R1：库存、鱼护与菜单交易合同

2026-10-24。状态：面向 P1 数据基础和 P8 经济的独立规格，尚未实现或通过游戏验收。本文补充[开发计划](DEVELOPMENT_PLAN.md)的库存与交易前置要求，沿用[浮漂装配规格](FLOAT_RIG_ASSEMBLY_SPEC.md)的实例归属及出手消耗规则。P0 门槛不变，不恢复暂停中的界面和玩法编码。

买卖、食品补给和换装从任意钓点的菜单进入，地图移动只用于寻找钓点。当前位置、到商店建筑的距离和场景碰撞不能成为交易条件。“任意钓点”不等于任何钓鱼状态都能修改装备：活跃会话、保存恢复及授权限制仍按以下合同执行。

## 数据与归属

| 对象 | 必要信息 | 不变量 |
| --- | --- | --- |
| 玩家存档分支 | `profileId`、`saveGeneration`、格式/规则版本、最后确认提交序号 | 一个分支只允许一个状态持有者写入；恢复旧备份不得继续接收新分支的迟到写请求 |
| 钱包 | `currencyId`、整数 `balanceMinor`、钱包版本 | 不为负，不超过声明的范围；加减及乘法检查溢出，禁止浮点货币累计 |
| 装备实例 | `instanceId`、型号、状态版本、耐久及唯一位置 | 同型号可持有多件；装备、穿戴、卸下和出售移动同一实例，不复制型号对应的物品 |
| 消耗品堆叠 | `stackId`、型号、整数数量、批次/品质/时效属性、交易标记、版本 | 数量非负；只有合并键完全一致的堆叠可合并；鱼饵和食品分别持有 |
| 线材 | 库存长度或已分配线段及其 ID/来源/位置 | 沿用装配规格的长度守恒；商品线、已绕线及回收线段不能重复计入可用长度 |
| 渔获实例 | `fishId`、来源会话/入护事件、鱼种、整数质量、来源水域、获得记录、状态版本、位置、计价来源 | 同一条鱼只在一个位置；入护、出售、放流等终结事件可追溯且不能重复结算 |
| 交易报价 | `quoteId`、对象/数量快照、逐项金额、总额、目录/价格版本、相关状态版本、有效条件 | 由状态持有者生成，绑定一次购买或出售意图；页面修改金额不能改变结算 |
| 交易回执 | 请求及意图 ID、命令指纹、提交序号、前后余额、对象增减/移动、版本、规则版本 | 与业务变化一起确认；显示“成功”必须能查到同一份已提交结果 |

本项目货币使用整数最小单位，定义 100 个最小单位为 1 银币。这个表示方式是本项目决定，不是对 RF4 的货币实现推断。未来目录价格、免费项目标记及最大余额必须明确配置；缺价格不是零价。重量、线长等沿用装配规格的整数单位，页面只负责显示换算。

库存位置、钓组槽位、穿戴位和容器内位置互斥。一个容器不能直接或间接包含自身，所有引用必须存在。已绕线的渔轮放入背包时保留同一线段关联，不能额外发出一份线材。装在钓组或穿在身上的物品仍属于玩家，不能作为背包里的另一件可售物品出现。

鱼饵选择只是对堆叠的引用，不额外占有或复制数量。拆分堆叠、绕线、拆装和购买等命令必须检查活跃引用；删除旧堆叠 ID 的合并操作须在同一提交内更新所有允许更新的引用，或明确拒绝。不能留下悬空的鱼饵选择。

## 容量与可操作状态

背包容量按顶层库存位置计数：一件顶层装备、一个堆叠、一份顶层线库存/线段各占一个位置；同一容器内的部件不再作为顶层物品重复计数。穿戴位和钓组槽位另有数量约束。各容器容量、堆叠上限及可接收类别由规则表明确规定，不用显示卡片数推断真实容量。

合并已有堆叠后仍放不下的购买整笔拒绝，不能先扣钱再把部分物品丢到不可见位置。卸下或替换装备按完整事务的最终位置检查容量；旧件回包、新件离包同时发生时，只检查最终有效状态，不因临时执行顺序造成假满包，也不放宽真实容量限制。

鱼护与背包分别计容，鱼护以持有条数约束；未来若增加质量/体积限制，要新增规则版本和迁移政策，不能悄悄丢弃超额旧鱼。渔获入护必须再次原子校验容量，成功时与入护事件、数量和对应奖励记录共同提交；失败不得给出“已入护”或重复授予经验。入护未完成时的收束由 P3/P4 定义，不能为了腾位置自动卖掉或删除另一条鱼。P5 多竿必须在同一写入者中竞争剩余容量，不能各自先承诺同一个空位。

首版选择与[收鱼合同](FIGHTING_MODEL_SPEC.md)一致，是本项目简化设计而非RF4行为复现：容量不足是明确拒绝，保留本次同一会话/遇鱼的待处理状态，冻结全部模拟并清除持续输入；当前鱼未入旧鱼护，不发入护奖励。该受控结果只允许查看和有当前授权、分支/会话/遇鱼/版本校验的`ReleaseCurrentFish`明确放流一次，不开放出售/放流旧鱼、换鱼护/容量或整理后重新入护。先解决/收束全部会话，再按一般门槛管理旧鱼护和重新就绪；放流当前鱼本身不腾旧位置。保留/换鱼以后须另作原子交换扩展。

放流当前鱼是P4终结命令，不是普通鱼护管理的活跃交易例外；结果暂停只停模拟，合法交互结果命令仍可确认，不能绕过独立宿主/授权门槛。其终结、已配置奖励/损失和回执一次提交，奖励缺配置不发且不阻止无奖励收束。容量拒绝没有入护写入，不等同`persistence-uncertain`；放流提交若不确定则停新写入、先查询原回执，不先退款/再放流/恢复收竿。已确认终结优先，未完已出手会话的重启仍按既定恢复收竿处理，无鱼或奖励。

| 状态 | 菜单及交易规则 |
| --- | --- |
| 无活跃会话，存档可写 | 任意钓点可报价、买卖、管理库存及装配 |
| 蓄力、松开但未出手 | 先确认取消，废止旧出手身份，再接收修改库存的命令；取消不扣出手资源 |
| 已出手至收鱼/收竿结束 | 可以查看信息；交易和涉及该会话的库存修改返回 `session-busy`，先按已有流程收束。打开菜单不自动退款、结束会话或完成一次出售 |
| 入护因容量不足而待处理 | 全部模拟暂停，仅按P4授权与身份校验明确放流当前鱼；旧鱼护仍只读，不允许出售/放流旧鱼或改容量来重试入护 |
| 已入护结果等待页面展示结束 | 已确认的鱼可正常查询；是否允许直接出售必须使用同一鱼实例和原入护回执，不能再次入护或再发经验 |
| 观赏页、失效授权、旧文档 | 只读；已有请求 ID 不构成新的写入授权 |
| 保存恢复中或结果不确定 | 不接收新业务写入；只展示恢复状态、已验证快照和可查询的确定回执 |

菜单暂停、失焦或关闭只改变交互状态。已经受理的原子交易不能因页面关闭而执行一半，未受理的选择也不能在恢复后自动确认。

## 购买、装备与食品

购买按“选择商品和数量 → 获取报价 → 明确确认 → 等待已确认回执”进行。报价包含每包份数和实际入库数量；页面不能把“购买 2 包”和“增加 2 份”混为一谈。数量必须为正整数，型号、销售类别、解锁条件、规则和库存上限均由状态持有者检查。

成功购买一次完成余额减少、实例/堆叠增加、容量及版本变化、交易意图消费和回执确认。新实例 ID 在这笔提交中确定；丢失响应后的重试返回原 ID，不能重新生成物品。报价 ID 成功使用后不得通过更换请求 ID 再次购买；再次主动购买需获取新的意图与报价。

首版购买只入库存，不隐式装备、食用或绕线。装备替换执行装配合同；食品使用作为独立命令扣一份并施加一次已配置效果。0.3.1 的“购买即食用”和“购买即装备”是旧行为，不能在迁移时假定这些操作留下了未食用食品或额外装备。若 P8 后续增加“购买并使用”快捷操作，须另定义一次原子复合命令，不能串接两个无恢复保证的按钮回调。

食品效果、服装效果、商品补货、二手装备回收及维修尚待 P8 配表。非鱼物品仅在目录明确允许回收时可报价；装配中、穿戴中、被会话占用的实例不得出售。带子物品的容器和渔轮不得隐式连同内容物卖出：先拆分，或在以后专门定义的整组报价中列全对象，当前未定义时拒绝该操作。

## 单卖、多选与批量卖鱼

单卖和多选使用同一 `SellFish` 命令，区别仅是明确的 `fishIds` 集合大小。“全部卖出”必须在玩家确认时冻结实际鱼 ID 清单，并显示条数、总质量和总价；不能保存一个 `all: true` 标志，等异步执行时再卖掉后来入护的鱼。

搜索、排序和筛选不改变所有权。界面必须区分“卖出选中的 N 条”和“卖出鱼护全部 N 条”；筛选结果发生变化不能悄悄扩大原选择。空集合和重复 ID 拒绝，不能重复计价后只删除一次。

报价及提交须核对每条鱼仍在当前鱼护、未出售/放流、版本匹配且计价参数存在。批量出售采用全成或全败：只要一条鱼不存在、已被另一笔交易处理、版本变更或报价失效，本笔全部拒绝，不先卖掉其余鱼。新报价应基于最新选择重新确认。

成功提交一次完成全部指定鱼的终结状态/移出鱼护、钱包增加、`sold` 计数及交易回执。鱼的历史钓获数、图鉴和个人纪录不随出售删除。出售本身不再发一份入护经验；未来若有出售任务或成就奖励，必须用对应业务事件另行防重，不能通过重放回执触发。

鲜度和计价属于原创待配规则。P8 必须声明使用哪种时间基准、菜单/宿主暂停和离线时间是否计入、每条鱼的价格舍入位置及规则变更政策；当前未定义这些参数时，相关新鱼不能被默认为“全新鲜、零折扣”继续计价。报价记录价格规则版本与评估时点，结算时若已不满足其有效条件，返回 `quote-changed`，展示新金额并要求重新确认。不能用系统时间回拨静默恢复鲜度。

迁移的旧鱼采用下文明确的兼容计价记录，不因旧版本没有鲜度字段而凭空给出腐败、全新鲜或额外加价。

## 原子校验、一次结算与回执

所有经济写入由唯一状态持有者串行校验和提交。页面提交的是意图，不能直接写钱包、库存或存档。命令至少带当前存档分支、请求 ID、报价/业务事件 ID、明确对象与数量，以及相关预期版本。请求 ID 为规范 UUID；集合按稳定顺序规范化，金额及数量严格校验，命令指纹不能只比较原始 JSON 属性顺序。

一次接收按以下顺序执行：

1. 验证当前文档授权、玩家及存档分支。旧授权不能借已有回执越权。
2. 查询该分支已受理的请求身份。同 ID、同业务内容返回已确认原回执；同 ID 改内容返回 `request-conflict`。去重先于余额/版本/报价过期检查，因此合法新会话重试旧成功请求不会被当前状态误拒绝。
3. 检查报价/入护等业务身份是否已消费，防止改一个请求 ID 绕过业务防重。
4. 校验状态、版本、归属、数量、规则、报价、容量、余额和所有算术范围。在独立候选状态中得到完整变更，不对当前对象逐项提前修改。
5. 将完整变化、意图消费、业务终结身份和回执交给正式保存层的同一原子提交；确认提交后才发布新状态与成功消息。

预期版本、对象集合、数量和报价属于命令语义；重试必须保留原值。新的页面授权凭据属于传输上下文，不纳入经济命令指纹，因此重启或重新授权后能查询原意图。改变选择、数量或接受新报价应产生新意图；仍不确定的旧意图必须先恢复查明，不能直接换 ID 下单。

规范示例，ID 与序号只说明结构，不是来自用户数据：

```json
{
  "type": "SellFish",
  "profileId": "3861543c-6421-45fb-9c03-35f5fb09c94c",
  "saveGeneration": "6f67984d-1c5f-44cb-ae54-47c7dd8d6fe2",
  "requestId": "be495330-8b68-48ed-a6b2-97c3d31ea54d",
  "quoteId": "28c4c8db-e8ae-4b5f-b8b4-a42fbcc08035",
  "fishIds": [
    "6fc98454-6e2e-4831-abd0-44912426ca67",
    "c803cd58-4b92-4bfb-a86c-b03d75633ba6"
  ],
  "expectedWalletRevision": 12,
  "expectedCreelRevision": 8
}
```

页面不提交可信售价。回执返回实际逐项金额、总额、前后余额、售出鱼 ID、提交序号及新版本；重复应答可增加 `duplicate: true`，但不能改写原经济结果。购买对应 `BuyItems`，使用同一交易骨架和冻结的商品/数量清单，不接受页面自由指定赠品或价格。

最终业务拒绝要明确“未提交”，修正资源或选择后由玩家发起新意图。保存层应保留所有已受理意图的语义绑定与确定结果；不能仅因换页、重启、回执缓存淘汰或压缩日志，就把旧成功意图当成全新交易。正式持久化格式、回执保留及压缩方案由 P1 另行设计和验证。

## 失败、重启与不确定结果

| 结果/错误 | 业务状态与恢复方式 |
| --- | --- |
| `insufficient-funds` | 一件物品也不入库，余额不变；可卖鱼、取消选择或获取符合条件的救济补给 |
| `inventory-full` / `stack-limit` / `creel-full` | 全笔拒绝，不部分扣款或丢弃对象；允许查看和清理已有库存/鱼护 |
| `stale-state` / `quote-changed` | 无结算，返回最新可读版本及原因；刷新后重新确认，禁止自动接受更高购买价或更低售价 |
| `item-in-use` / `session-busy` | 无结算；按装配或会话合同结束占用，不以出售强行取消出手 |
| `fish-unavailable` / `duplicate-selection` | 批量整笔拒绝；不能过滤掉错误对象后自行售出剩余部分 |
| `configuration-missing` / `amount-out-of-range` | 无结算；不能以零价格、默认容量、负数量或溢出后的金额继续 |
| `request-conflict` / `intent-already-settled` | 保留原结果，不新建经济变化；合法查询可返回已确定的关联结果 |
| `save-capacity`，保存层确认尚未开始写入 | 新交易拒绝，已确认库存和余额不变；仍可查询旧回执。不能误标为不确定提交并撤销所有读取/重试能力 |
| `persistence-uncertain`，可能已经写入 | 禁止新经济写入，不自动退款、不再次扣款、不生成补偿物品；重启/恢复核验后再按原意图查询 |
| `save-corrupt` / `save-missing` / `unsupported-save-version` | 进入恢复或只读状态，保留证据和备份；不能静默调用新玩家初始化覆盖旧进度 |

确认丢失不等于交易失败。恢复后若发现原提交已完整确认，返回同一回执；如果正式保存协议能够证明未提交，才解除该意图的不确定状态。无法证明时继续阻止写入，不以“没查到一行日志”断言没有成交。

状态发布与页面应答必须来自同一已确认提交。页面可以显示“正在保存”，但不能先把余额动画当成成功，随后在下一次刷新还原。新页面取得当前完整快照，不用回执内的旧余额覆盖更晚的余额；原回执只用于说明那笔交易发生了什么。

P1 须区分完整旧快照、完整新快照、未完成写入和无法验证的数据；同时考虑日志整体截短、文件丢失和备份选择，不能只验证现存记录之间的 checksum 链。校验和可用于发现意外损坏，不是身份认证或反作弊证明。提交时发生 I/O 错误、进程终止、文件替换及真实断电的证据等级必须分别记录。

无钱、无饵且无法通过现有渔获继续游戏时，P8 要提供菜单救济路径。补给内容、领取条件与资格恢复由原创规则表定义，每次资格有可持久化的事件身份；重复点击不能重复发放。救济物品明确标为不可出售，不可被交易或制作转换成无条件刷钱渠道。没有配置和验收前不能把该路径标成已经解决资源困局。

## 0.3.1 迁移与回退

已核对发布提交 `e0e1ba7`：旧保存位于本项目页面的 `localStorage` 键 `fishing-desktop.progress.v1`，对象版本为 `version: 1`。这说明的是源码使用的存储入口，不是已定位或读取了某个玩家的文件。不同浏览器、壁纸宿主和页面来源的存储可能各自独立，不能搜索后自动把它们合并成一份资产。

| 旧字段/行为 | 新格式迁移要求 |
| --- | --- |
| `coins` | 对有效旧整数余额按 1 旧银币 = 100 新最小单位精确转换，校验范围并记录前后值；不重发初始余额 |
| `baits` 与 `bait` | 每种实际持有份数映射为堆叠并保留选择；分包只改变结构、不增加数量；旧数据缺字段需有明确兼容政策 |
| `owned` | 原来是已拥有型号集合，不是多件实例清单。每个有效唯一型号只映射出政策声明的一件旧资产；重复迁移复用同一映射，不能再次发物品 |
| `gear` | 原来仅选择竿、线、服装型号；引用映射后的同一旧资产。旧数据没有渔轮、钩、漂、线长或耐久，不能据此假造已齐全的新钓组 |
| `fish` | 保留每条有效鱼的身份映射、鱼种、重量、水域和兼容售价；迁移不是再次钓获，不触发经验、图鉴或记录奖励 |
| `book`、`xp`、`caught`、`sold` | 分别保留已有统计，不能用当前鱼护重新生成历史数量或再加一次经验；已出售历史不要求从鱼护反推 |
| `world`、`map`、`spot`、`journal` | 保留已支持字段或无损保留于兼容区；地点及最近记录不自动转成额外鱼实例。当前旧 `journal` 最多保存 30 条，不能宣称恢复更早丢失的记录 |
| `energy` | 按明确的旧体力到新刻度映射保留；不能因为格式变化免费补满 |
| `nextId` | 保留为旧身份映射来源之一；新实例身份由迁移清单确定，不继续用当前鱼护最大值生成可能冲突的 ID |
| 食品 | 旧版购买即消耗，没有未食用食品库存字段；不能按累计购买、体力或默认商品生成食品 |

旧鱼没有可靠的现实捕获时间和鲜度字段。有效旧鱼使用 `legacy-0.3.1-locked` 计价来源及 `legacy-unknown` 鲜度标记，保留按发布版原创规则核验过的旧售价，不补造时间，不因启用新鲜度制度立即扣价。旧记录中的 `value` 若与该版本的可核验规则不符，列为待处理冲突，不直接相信、悄悄重算或强制丢弃该鱼。

旧重量可保留原十进制来源值，并按声明的换算规则生成新整数质量；任何精度调整都出现在迁移报告中。旧线材的型号权益必须保留，长度、耐久、独立线杯和其他缺失参数由专用迁移配表明确补齐或作为兼容资产保留；这些原创政策未定前，不宣称该旧资产已满足新钓组就绪条件。需要新增入门配件时，须显式列为一次迁移补助，绑定迁移身份，不能靠重新载入反复领取。

迁移按“只读检查 → 保留来源备份 → 生成独立候选 → 对账验证 → 激活新格式”进行：

1. 先停止该来源的旧写入并固定一份读取快照；记录版本、来源标识、内容校验和及迁移工具/规则版本。备份和个人数据只留本地，不进入公开仓库。
2. 原始内容与可恢复导出备份完整保留；不得先调用旧 `restoreProgress()` 再把清洗后的对象称为原始存档。旧函数会默认填值、限幅、筛除鱼和重算售价，不能提供无损迁移保证。
3. 在独立候选位置建立稳定的旧 ID → 新 ID 映射与迁移身份，生成余额、鱼护条数/逐条映射、份数、已拥有型号和历史统计对账表。相同来源快照重试返回同一迁移，不追加资产。
4. 重复鱼 ID、未知型号、非法金额/重量、容量缩小、缺失必要规则或不能解释的差额均阻止激活，保留原数据和报告。不能静默去重、裁剪超额鱼、重置为初始 120 银币或赠送默认饵来掩盖问题。
5. 候选经过加载、完整性及恢复检查后，才在正式保存层支持的切换点激活；迁移中断只能继续校验该候选或回到原来源，不能同时把两份存档合并结算。
6. 激活新格式后旧程序不继续写同一玩家分支。旧保存键和备份保持原内容，新格式使用独立存储身份，不把新对象覆盖到旧版只能读 `version: 1` 的入口。

回退定义为返回迁移前的确定检查点：关闭当前分支的写入权限，保留新格式分支及其后续进度，再以原 0.3.1 数据启动旧版。明确告知该检查点之后的新交易不会被反向转换到旧版。不能同时保留新版本买到的物品又恢复旧余额；也不能把回退后的新增旧进度自动叠加到新分支。再次迁移需要明确选择来源和新分支，不能沿用旧分支的请求权限。

以上规定可回退的语义及验收要求，不指定完整磁盘布局、事务日志/数据库产品或自动备份周期；这些由 P1 保存方案补充。当前没有修改个人存档，也没有执行迁移。

## 待实现验收场景

| 场景 | 必须观察到的结果 |
| --- | --- |
| 不同水域、不同钓点打开商店/鱼市 | 使用同一菜单服务，无需接近建筑；相关条件不含角色到商店距离 |
| 买两件同型号装备后重试原请求 | 生成两件不同实例；重试返回原两个 ID，只扣一笔钱 |
| 新请求 ID 重发已使用的购买报价 | 业务身份防重，不再次扣钱或发物品 |
| 满包购买，或合并后仍超容量 | 钱包和库存都不变，不出现部分发货 |
| 满包内原子换件、卸下带线渔轮 | 按最终容量校验；线段仍只存在一份，失败时归属全保持 |
| 出售装配中、穿戴中或被会话引用的物品 | 指出占用原因，不取消已出手会话、不移除部件 |
| 单条、多选、全部卖鱼 | 精确出售冻结的 ID 集合，余额增加等于回执逐条金额之和；历史纪录保留 |
| 批量选择包含重复 ID、失效鱼或空集合 | 整笔拒绝，没有双倍计价或部分售出 |
| 打开全部出售确认后另一条鱼入护 | 后入护的鱼不进入原报价；版本冲突时刷新确认，不扩大出售集合 |
| 两个页面同时售出重叠鱼集合 | 只有第一笔有效提交成功；另一笔整笔拒绝，余额及 `sold` 不重复增加 |
| 钱包不足、金额溢出、缺价格、报价变化 | 无资源变化；有明确可恢复原因，不默认免费或接受新金额 |
| 提交成功后页面关闭或确认消息丢失 | 新授权查询同请求返回原结果，即使旧预期版本和报价已过期也不再次结算 |
| 同 ID 改内容，旧文档重试，新分支收到旧请求 | 分别拒绝指纹冲突、失效授权和分支不符，不授予新写权限 |
| 预写入容量拒绝与中途写入错误 | 前者无业务变化且旧回执仍可查询；后者进入不确定恢复，不自动退款或换 ID 重下单 |
| 满鱼护后重复放流当前鱼、卖旧鱼/换容量及放流确认丢失后重启 | 容量拒绝与保存未知分开；旧鱼护不变，当前鱼只终结一次，不确定先查原回执，全部会话收束后才管理旧鱼护再抛 |
| 写入中断、重启、数据整体截短或丢失 | 不显示虚假成功、不静默新建玩家；按正式保存协议确认完整结果或保留阻塞/备份 |
| 同一次入护事件及出售回执反复到达 | 鱼、经验、图鉴、计数各自只在原业务结算点增加一次 |
| 无钱无饵时重复领取救济 | 只有一次有效资格发放，物品按规则不可出售，能恢复合法继续游戏的路径 |
| 有余额、鱼护、装配选择及历史统计的 0.3.1 样本迁移 | 所有保留项目可逐项对账；不重复发经验、初始钱、食品或装备 |
| 同快照重复迁移，中断后再次启动 | 稳定 ID 和同一迁移结果，不叠加资产，不改原始备份 |
| 旧数据冲突、容量减少或新参数未配置 | 阻止激活并保留原样本，报告实际差异；不裁剪鱼护或补默认值冒充成功 |
| 新格式发生交易后回退，再选择恢复新分支 | 两个检查点各自完整保存，不合并两份余额/物品，不让旧请求影响另一分支 |

这些是 P1/P8 及其集成阶段的验收要求，当前没有把任何一项列为通过。正式保存实现、故障注入、真实宿主交互和断电证据应分别记录；菜单原型能点通不代表经济持久化已达标。
