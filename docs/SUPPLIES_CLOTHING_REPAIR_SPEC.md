# R1：食品、穿戴与菜单维修合同

2026-10-26。面向[开发计划](DEVELOPMENT_PLAN.md)P8的原创前置规格，尚未实现或通过玩法验收。继承[输入状态](INPUT_RIG_SPEC.md)、[装配/出手](FLOAT_RIG_ASSEMBLY_SPEC.md)、[库存交易](INVENTORY_TRANSACTION_SPEC.md)、[遛鱼](FIGHTING_MODEL_SPEC.md)与[成长/制作](GROWTH_CRAFTING_SPEC.md)合同，不改变P0→P1的阶段门槛，不恢复暂停的界面或玩法编码。

补给购买、食用、换装和维修均从任意钓点菜单进入；不检查距建筑的距离，不新增跑商路线。菜单可以查看所有状态，但能否修改仍受会话、授权与保存门槛约束。

## 依据、旧行为与未知项

RF4截图可参考食品/服装分类、状态条和装备信息层级；客户端结构只能证明相关面板/类型存在。原版体力、饥饿、服装、磨损与维修的公式、真实数值和等待时间未恢复，本文不宣称复刻这些规则。

已核对本项目[src/content.js](../src/content.js)和[src/game.js](../src/game.js)：0.3.1仅有`energy`，买茶/三明治立即扣钱并恢复体力，满体力拒买；没有未食用食品、饥饿、耐久或维修。买装备即装备，服装仅是型号选择：防风服降低每抛体力成本，遮阳套装通过`wait`加快问饵；竿/等级另有简化收鱼加成。这些是旧原创玩法，不是RF4公式，也不自动成为P8参数。

## 数据与规则入口

| 对象 | 必需信息与约束 |
| --- | --- |
| 人物补给状态 | `stamina`、`satiety`、各自上限、状态版本、规则版本、活动计时余数；非负有界整数，饱食度越低表示越饿 |
| 食品堆叠/使用意图 | 沿用具体`stackId`、批次/品质/时效、数量与版本；使用指定一份、作用对象版本、规则及业务意图，不能只提交商品型号 |
| 穿戴 | `slotId → instanceId`、穿戴版本；同一实例只有一个位置，槽位类别与互斥表明确；首版一套服装位，不凭旧“帽子”型号额外生成帽位 |
| 耐久 | 每个可磨损实例的整数当前值/上限、状态版本、磨损/可修复规则版本；不可用状态与实例归属分开，坏件仍有原ID |
| 维修报价 | 具体实例与预期版本、修前/修后值、费用、材料及其批次、维修规则、适用条件、报价/意图ID；结果和全部成本可预览 |

资产沿用整数货币最小单位（100单位=1银币）、数量及装配单位；体力、饱食度、耐久采用各自声明刻度。比例用有界定点/整数分子分母，统一舍入位置，活动余数不因重载或每帧取整丢失。页面百分比不得反写资产。

目录须显式声明恢复量、消耗/恢复活动、上限、效果叠加顺序、磨损来源、损坏门槛、可修复性和报价算法。零效果、免费或确定性服务只能由明确配置表达；缺参数返回`configuration-missing`并禁用受影响操作，不能补零、免费、满修或必成。

## 食品持有、使用与活动时间

购买仅入库存，按交易合同检查容量和整数数量，不自动食用。使用是独立`UseFood`意图：检查唯一写入者、授权/分支、版本、当前可操作状态、具体批次仍可用且至少一份，再在候选状态计算实际恢复。份数减一、人物状态变化、版本与回执同一事务确认；动画、音效和菜单关闭不负责扣物品或恢复数值。

首版食品仅立即恢复配置的体力/饱食度，不引入持续药效或离线食用队列。恢复截在各自上限，确认预览显示实际增量及被截部分；两项实际增量均为零时拒绝且不消费。预览后状态变化则版本冲突，不能按旧显示悄悄浪费食品。批量食用首版不开放，不能以重复按钮模拟同一份多次作用。

首版只消费统一有效模拟时钟：按规则声明的行走、等待、收线等活动及固定步数更新饱食度/体力，不使用绘制帧数或墙钟。活动对应速率及是否恢复必须逐项明确；未接通的活动不开放相关效果。菜单、失焦、观赏模式、宿主暂停及离线均不推进，不因睡眠/重启一次补算消耗或免费恢复。食品时效首版也使用该活动时钟，批次记录版本与到期点；若未来改用现实时间，须另立迁移/防回拨合同。

饥饿档位由饱食度阈值推导，首版通过明确配置影响体力恢复率和新动作成本，不直接改变鱼群、售价或竿线强度。动作成本按版本化顺序组合基础成本、饥饿档位、服装和技能效果，末尾量化一次并校验上下限；新出手仍按装配合同原子扣一次成本。体力不足拒绝开始该动作，零体力不凭空判定鱼已脱钩；持续收线的耗尽处理须由P4明确接通并可观察，缺该规则不得启用持续消耗。

## 穿戴、快照与会话门槛

`EquipClothing`/卸下指定实例与槽位，校验归属、类别、资格、耐久可用性、预期穿戴/库存版本及最终容量；旧件回包与新件移入穿戴位同一提交。不能把已穿物品另作背包可售副本，也不能在满包时先丢旧件。合法脱下不发新手服装或退款。

效果只从已穿且可用实例产生，绑定来源ID、效果规则及叠加顺序；首版只启用有完整接口的体力成本/恢复修正。旧遮阳套装的问饵加速不自动继承，服装不统一乘竿力、线强度或钓获概率；未来新增效果须说明实际作用接口与验收。

| 当前状态 | 食用、换装与维修 |
| --- | --- |
| 无活跃会话，正式存档可写 | 允许按合同受理；任意钓点相同规则 |
| 蓄力/释放后尚未出手 | 先确认取消并废止旧出手身份，再接收新意图；取消后修改失败也不恢复旧蓄力 |
| 任一竿已出手至终结待确认 | 查看可用，食用/换装/维修首版统一返回`session-busy`；切换手持竿不能绕过其他竿会话 |
| 只读页、恢复中、结果不确定 | 不受理新业务写入；只查询确定快照与原回执 |

每次出手冻结同一技能、穿戴、装备起始耐久与规则快照；后续显示、规则热更新或迟到请求不能回写该会话参数。活动体力/饱食度是共享人物状态，由owner串行更新，不复制进每竿钱包；会话内哪些动态体力修正生效必须随快照规则声明。快照不冻结合法磨损：P4按冻结的磨损规则从起始耐久及本会话累计量求当前有效状态，不能每步重读后来换过的库存。

首版不启用共享服装的搏斗磨损；每竿装备磨损仍只属于该钓组。以后若启用多人次会话共享的穿戴损耗，必须由owner按实例合并各来源增量、保留共同余数并串行确认，不能让多竿分别用同一起始耐久覆盖彼此结果。制作门槛沿用成长合同，能否使用无关材料另按配方动作条件判断；不能推断本表已禁止所有制作。

## 磨损、坏件与同步维修

磨损来源只能是明确的出手/使用/搏斗/制作业务事件或owner固定步累计的负载；不按渲染帧、菜单次数或重载次数扣耐久。累计保留规则规定的余数，资产写入只在声明的确认事件处量化一次；来源事件ID与损耗通道防重。持续搏斗磨损由P4终结事务与物品损失、渔获及奖励一起结算；制作工具磨损沿用制作事务，不能再被P8重复扣一遍。

运行中达到不可用门槛，由P4固定终结优先级处理一次故障，禁止再借修理或切竿继续使用；故障不等于删除整套钓组。可留存坏件保留ID和归属，实际断线/丢钩等只移动或移除明确损失对象，线长按原合同守恒；维修不补回已丢部件、鱼饵或断掉线长。哪些部件可修、不可修或需替换必须目录明示，不能把所有消耗品都修成新品。

首版采用同步维修：选单件→生成完整报价→明确确认→一次原子服务，不设维修等待队列。报价必须显式声明确定性结果、修后上限/可能永久损耗及全部成本；不是将未知失败率当零。保留同一实例ID，费用/材料扣除、耐久结果、版本与回执同一提交，不能先扣款再异步“发新件”。满耐久、不可修、缺报价规则或不足材料/余额均受理前拒绝。

首版维修对象须先从钓组/穿戴位卸入可用库存；被容器、制作意图或会话占用时拒绝，不隐式拆散渔轮和线杯。卸件按装配合同独立确认；随后维修被拒绝不自动装回或回滚已确认卸件。报价失效、对象换位/磨损、材料先被使用均重新报价并确认，不沿用旧价。未来若引入等待，须另定预留、活动计时、取消退还、恢复及容量合同；当前不能后台倒计时或离线完工。

这里的容器占用包括对象仍在另一容器内；对象本身若保留线杯、绕线或其他子件关系，首版也拒绝直接维修。带线渔轮卸回背包后按装配合同保留原关系，须由玩家显式完成合法拆分/卸线后再报价；不能为了维修清空子件、删除线长或悄悄生成空轮。未来允许带子件维修须单立兼容和容量规则。

## 取消、故障恢复与迁移

报价/预览未确认可取消，零消耗零效果；事务一旦受理，关闭页面、失焦或取消表现不能撤销一半。请求同ID同内容返回原回执，同ID改内容拒绝，换ID不能重用已消费业务意图；详细授权、校验顺序和台账沿用库存合同。业务拒绝与保存结果不确定分开：后者停止新写入并查询原回执，不先退款、补食品或再修一次。

重启有提交证明则恢复原消费/效果/耐久，无提交则原资产不变，无法判断则保留阻塞与备份。未完成已出手会话按装配合同仅执行一次`recovery-retrieve`：保留已确认消耗/损失，不凭空补记尚未提交的磨损或发奖励；因此首版不承诺恢复整段搏斗磨损。活动计时只恢复已确认检查点及余数，离线时间不生成恢复、修理完成或收益。

0.3.1体力按明确刻度映射保留，食品没有库存不能反推赠送；服装型号映射同一旧资产，不因购买即装备再发一件。旧数据没有的饱食度、耐久/上限、效果与维修历史须有明确一次迁移政策和差异报告；未定前保留兼容状态，不能静默补满、折损或宣称已具备新玩法资格。迁移重试、分支切换与备份沿用库存合同，不读取或改写个人存档。
